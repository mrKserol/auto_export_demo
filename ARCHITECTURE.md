# AutoExport Architecture

## 1. Backend

Backend на Python/FastAPI отвечает только за бизнес-логику и собственные данные системы.

В backend находятся:
- клиенты;
- автомобили;
- документы;
- статусы;
- проверки;
- операции с PostgreSQL;
- внутренние API;
- правила и бизнес-операции, которые должны оставаться единообразными независимо от канала или внешней интеграции.

Backend не должен превращаться в набор интеграционных endpoints для каждого внешнего сервиса.

## 2. n8n

n8n является интеграционным, оркестрационным и аналитическим слоем.

Через n8n реализуются:
- AI-агент "Джек";
- Telegram;
- MAX;
- Bitrix24;
- GPS/телематика;
- webhooks;
- внешние REST API;
- аналитические tools;
- маршрутизация;
- retries;
- расписания;
- синхронизация между внешними системами.

Bitrix24 и другие внешние сервисы подключаются через n8n, если нет веской архитектурной причины делать иначе.

## 3. AI-агент "Джек"

Джек является AI-агентом компании.

Правила:
- Джек не должен выполнять произвольные SQL-запросы напрямую к PostgreSQL.
- Для типовых бизнес-операций Джек использует backend tools / internal API.
- Для аналитических запросов Джек использует контролируемые n8n tools/workflows.
- Интеграции с Bitrix24, GPS, Telegram, MAX и другими внешними системами выполняются через n8n.

Примеры:

Бизнес-запрос:
"Джек, что там по клиенту Ивану Промыслову?"
→ n8n AI Agent
→ backend tool
→ PostgreSQL
→ ответ агенту

Аналитический запрос:
"Джек, сколько новых клиентов было за последний месяц?"
→ n8n AI Agent
→ analytics tool/workflow
→ контролируемый SQL/query
→ ответ агенту

Запрос во внешнюю систему:
"Джек, какая стадия сделки у клиента в Bitrix?"
→ n8n AI Agent
→ Bitrix tool
→ Bitrix REST API

## 4. Разделение ответственности

При добавлении новой функции сначала определяется её тип:

- бизнес-логика → backend;
- собственные данные системы → backend;
- CRUD и правила работы с PostgreSQL → backend;
- интеграция с внешним сервисом → n8n;
- orchestration → n8n;
- webhooks → n8n;
- retries и расписания → n8n;
- аналитика для AI-агента → n8n;
- маршрутизация между каналами → n8n.

## 5. Каналы

Telegram, MAX и будущие каналы являются только интерфейсами входа.

Каналы не должны содержать собственную бизнес-логику.

Пример:

Telegram ─┐
MAX ──────┤
Web ──────┤
          ↓
         n8n
          ↓
        Jack
          ↓
   backend / tools

Добавление нового канала не должно требовать переписывания backend.

## 6. Главная цель архитектуры

Цель архитектуры:
- минимизировать будущие переделки;
- не размазывать бизнес-логику по n8n workflows;
- не превращать backend в набор интеграционных костылей;
- обеспечить возможность легко подключать новые каналы и внешние сервисы;
- сделать систему понятной для сопровождения разработчиком и администратором.

Главный принцип:

Backend = бизнес-логика и собственные данные.
n8n = интеграции, оркестрация и аналитика.
Jack = AI-слой, использующий контролируемые tools.

## Правило для будущих изменений

Перед реализацией новой функции всегда сначала определить:
1. Это бизнес-логика?
2. Это интеграция?
3. Это аналитика?
4. Это канал взаимодействия?

Не добавлять новую логику в backend или n8n автоматически без определения правильного слоя.
